# Scoring feedback

This page describes what a submission gets back from scoring. It does not describe how
sessions are judged: checks, weights, thresholds and cap limits are internal and are never
exposed.

## Feedback format

Every scored session produces one feedback string. It never contains numbers, thresholds,
signal names or check names. It takes one of three forms:

| Form | Meaning |
|------|---------|
| `scored` | The session was scored and no area failed |
| `scored; failed: <area>, <area>, ...` | The session was scored; the listed areas did not pass |
| `hard_fail=<reason>` | The session was rejected outright with score `0.0`; no areas are listed |

The result also carries `category_scores`:

```json
{ "mouse_movement": 0.0, "keyboard": 0.0 }
```

Only the keys matter. A key is present when its area failed. The value is always `0.0`;
it is a marker, not a sub-score. A session with no failed areas has an empty object.

## Feedback areas

Failed areas are always reported in this order:

| Area | Broadly covers |
|------|----------------|
| `session_integrity` | Payload and session binding, collector health |
| `browser_environment` | Consistency of the browser environment |
| `graphics` | Rendering and graphics stack |
| `device_profile` | Plausibility of the device and hardware profile |
| `browser_engine` | Engine behaviour matching the claimed browser |
| `request_identity` | The request matching the identity the payload claims |
| `task_interaction` | Real interaction with the task target |
| `mouse_movement` | Pointer movement |
| `keyboard` | Typing |
| `input` | The input event sequence |
| `task_timing` | Pacing of the task steps |
| `interaction_pattern` | Behaviour across the whole session |

An area marked failed means something in that area did not look like a real user. The
feedback does not say what, or by how much.

## Hard fails

A hard fail is reserved for certain evidence. It forces the score to `0.0` regardless of
anything else in the session, and the first match ends the evaluation. Only the reason
code is returned:

| Code | Meaning |
|------|---------|
| `payload` | The payload or session binding is invalid, incomplete, duplicated or expired. The challenge API also uses this code for a wrong or incomplete task |
| `integrity` | The data collector was tampered with |
| `automation` | Definitive automation markers were found |
| `realm_mismatch` | Browser contexts of the same page contradict each other |
| `untrusted_input` | Task input was generated by a script, not by a user |

A hard-failed session reports no feedback areas.

## Caps

A cap is a ceiling on the score:

- The score is first computed as a blend of all checks. Every cap that applies is then
  collected, and the strictest one wins.
- Caps fire on strong bot indicators or on a lack of human evidence. A good result
  elsewhere cannot lift a capped score above its ceiling, and a capped session ends up
  below the passing level.
- Caps are never named in the feedback. A cap that fires only marks its area as failed:
  a graphics-related cap, for example, shows up as `failed: graphics`.

### Cross-run cap

The runs of one submission are also compared with each other. If they show replayed or
mechanically repeated behaviour, the whole submission is capped, whatever the individual
sessions scored.

## Other responses

These are not scores. The session is refused or not reported:

| Status | Meaning |
|--------|---------|
| `400` | Invalid session id |
| `404` | The challenge does not know the session |
| `409` | The session was already scored; only the first submission counts |
| `413` | The payload is too large |
| `422` | Invalid JSON or an invalid payload |
| `503` | Scoring failed internally. Nothing is reported, so the challenge applies its timeout score. There is no fallback scorer |
